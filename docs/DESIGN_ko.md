# Pixelwright 개발 판단과 v0.6.0 구현

사용자가 제공한 `pixel-art-qa-development-kit-v0.2.0 (1).zip`을 출발점으로 삼았습니다. 압축 파일의 지시문·로드맵은 검토 대상 자료입니다. 사용자의 목표는 GPT/Claude 공통 지원, Pixelwright 이름, 생성 전후의 균일한 픽셀 규격이며, 첫 대상은 정적 PNG입니다.

## 보장 범위를 생성 구조로 옮기기

기존 키트는 이미 잘못 만들어진 이미지의 문제를 찾는 검사기에 가까웠습니다. 픽셀아트 프롬프트를 강화해도 생성 모델의 출력은 사각형의 크기나 내부 RGBA가 일정하지 않을 수 있습니다. 새 생성 경로는 AI가 논리 색상 행렬을 작성하고, 결정적 렌더러가 각 셀을 하나의 색상으로 채워 정수 배율로 확대합니다. 렌더된 파일은 별도 검사기에 다시 넣습니다.

논리 캔버스가 `16×16`, 배율이 `8`이면 파일은 `128×128`, 모든 셀은 `8×8`입니다. 원본의 모든 셀에 같은 규칙을 적용합니다. 붙어 있는 같은 색상 셀들이 긴 직사각형·계단 형태가 되는 것은 정상입니다. 셀 규격과 클러스터 모양을 혼동하면 정상 그림을 잘못 거부하게 됩니다.

실루엣과 색상 설계 같은 미적 품질은 수학적으로 보장되지 않습니다. Skill은 내보낸 실제 그림을 보여 주고 논리 해상도에서 검수하도록 안내합니다. 일반 생성 모델 결과도 사용할 수 있지만 최초 상태는 미검증 후보이며, 격자 투영 결과는 새 파생 이미지로 기록합니다.

## v0.4.0: 복잡한 요청의 선택적 레이어 작업

레이어를 나누면 배경·아이템·UI·문구를 독립적으로 수정할 수 있습니다. 실제 배너에서 문구의 색상만 바꾸거나 별도의 장식 요소를 제거했던 작업이 이 기능의 계기입니다. 모든 요청을 분리하도록 강제하지는 않습니다. 단순한 아이콘은 한 작화로 만들고, 캐릭터의 손·방패·무기처럼 접점과 포즈가 맞아야 하는 요소는 한 그룹으로 제작하는 편이 안정적입니다.

Skill은 분리가 도움이 되는 요청에서만 `references/layers.md`를 읽도록 안내합니다. 먼저 구도·논리 크기·배율·공통 RGBA 팔레트·광원·앞뒤 순서를 확정합니다. 입력은 기존 생성·보정 도구가 만든 확대 PNG이며, JSON 레이어 목록에 입력 경로, 각 레이어의 논리 크기, 셀 단위 위치, 순서, 표시 여부를 기록합니다. 원본 행렬과 PNG는 유지하고, 목록 편집은 같은 폴더에 새 파일로 저장합니다.

`pixel_layers.py`는 세 명령을 제공합니다. `list`는 목록을 검증해 배치를 보여 주고, `edit`는 위치·표시 여부·순서를 변경한 새 목록을 만듭니다. `compose`는 모든 레이어를 검사하고 합성한 뒤 최종 PNG를 다시 검사합니다. 숨긴 레이어도 검사하므로 가림이나 표시 해제로 불량 입력을 합격시킬 수 없습니다.

합성은 논리 캔버스에서 수행합니다. 입력 PNG의 셀이 정확한 단색이고 공통 배율을 지킨다는 검사를 통과한 뒤 네이티브 셀을 얻고, 정수 셀 좌표에 불투명 셀만 덮어씁니다. 마지막에 공통 정수 배율로 확대합니다. 이 방식은 중간색과 비정수 위치를 만들지 않습니다. 반투명 혼합·회전·크기 변경·잘라내기는 지원하지 않으며, 지정 레이어 전체가 캔버스에 들어와야 합니다.

팔레트는 각 레이어에 따로 주는 대신 작품 전체가 공유합니다. 합성 모드는 `allowed_palette`, `max_colors`, `transparent_rgb: "exact"`를 명시적으로 요구합니다. 입력 레이어는 이진 투명도를 사용하고, 최종 프로필은 이진 또는 불투명을 선택할 수 있습니다. `max_colors`는 가시 RGB를 세므로 투명색을 포함한 32개 RGBA 팔레트는 보통 가시 색상 예산 31개로 표현합니다. 서로 다른 레이어가 각각 예산 이내여도 합성 후 색상 수가 예산을 초과할 수 있어 최종 검사가 필요합니다.

합격 산출물에는 두 단계의 검사가 모두 필요합니다. `layers.json`과 `layers/0000/qa/` 아래에 입력 검사 기록을, `final/`에 최종 검사 기록을 남깁니다. 모든 레이어와 최종 PNG가 PASS일 때만 출력 루트에 `native.png`와 `rendered.png`를 제공합니다. 입력이 실패하면 합성하지 않고, 입력은 통과했지만 최종 검사가 실패하면 `candidate/` 아래의 진단 후보만 남깁니다. 목록의 경로는 그 폴더 안의 상대 경로로 제한하고, 64개 레이어·총 48,000,000 입력 픽셀 상한을 적용합니다.

이 과정은 구조 품질을 확인하며, 최종 구도까지 판단하지는 않습니다. 각 레이어의 작화와 완성 장면의 비례·광원·손과 장비의 접점·가림·문구 가독성을 별도로 검수합니다. 격자 QA 이미지는 합성 입력이나 작품에 넣지 않습니다. 동봉 예제는 배경·기사·아이템·제목의 네 레이어를 공통 팔레트로 합성하며, 기존 기사의 방패와 둔기는 캐릭터 레이어 안에서 함께 유지합니다.

## v0.5.0: 재사용 팔레트와 색상 변환

기존 프로필의 `allowed_palette`는 허용 색상을 검사하고, 생성 명세의 `palette`는 행렬 토큰을 색상에 연결합니다. 여러 에셋에서 이름 있는 색상과 명암 램프를 재사용하려면 검사 제약과 작화 데이터를 구분한 라이브러리가 필요합니다. 새 라이브러리는 `schema_version`, 선택적인 `name`, 색상 토큰을 담는 `colors`, 토큰의 순서를 담는 `ramps`를 사용합니다. 프로필을 대체하거나 자동으로 변경하지 않습니다.

`pixel_palette.py`는 세 명령을 제공합니다. `extract`는 PNG에서 관측한 전체 RGBA 값을 빈도순으로 골라 새 라이브러리를 만들며, 같은 빈도에서는 RGBA 채널 순서로 정렬합니다. 기본 상한은 256색이고 `--max-colors`로 줄일 수 있습니다. 상한 때문에 빠진 색상은 보고서에 기록합니다. 기본 `exact`는 알파 0 아래의 RGB도 구분하고, 명시적인 `visible`은 추출할 때 그 RGB를 정규화합니다. 어느 경로도 원본 격자를 추정하거나 PASS를 판정하지 않습니다.

`ramp`는 같은 알파를 가진 두 끝 색상의 인코딩된 sRGB 바이트를 정수 half-up 반올림으로 보간합니다. 2~256개의 서로 다른 단계를 만들며, 반올림으로 중복 색상이 생기면 거부합니다. `--name`은 램프 이름이고, `--palette`는 기존 라이브러리를 새 파일로 확장하는 선택입니다. 기존 색상과 이름을 보존하며 같은 색상을 재사용하거나 토큰을 추가합니다. 지각적으로 균등한 색상 간격이나 재질별 명암을 자동으로 설계하는 기능은 아닙니다.

`remap`은 이미 유효한 격자의 색상만 바꿉니다. PNG를 원래 프로젝트 프로필로 검사하고, 기하·셀 내부 RGBA 단색·알파 규칙이 맞을 때만 논리 셀을 가져옵니다. 변환 전의 색상 수나 허용 팔레트 위반은 기록하되, 그것만으로 색상 변환을 막지는 않습니다. 각 색상을 알파가 같은 목표 색상 중 인코딩된 sRGB 거리 제곱이 가장 작은 값에 매핑하며, 거리까지 같으면 먼저 선언된 목표를 고릅니다. `--ramp`를 지정하면 해당 램프와 라이브러리의 알파 0 색상을 함께 목표로 삼으므로 투명 셀을 유지하며 재질 색상을 제한할 수 있습니다. 반투명 셀도 변환하려면 해당 알파의 목표 색상이 필요합니다. 셀 위치·배율·크기·알파는 유지하며 격자 보정이나 알파 임계값 처리는 수행하지 않습니다.

최종 PNG는 원래 프로필과 선택한 목표 색상을 모두 만족해야 합니다. 라이브러리 안에 실제로 사용하지 않은 허용 밖 색상이 있어도 에셋을 거부하지 않으며, 출력에 그 색상이 쓰이면 최종 검사가 실패합니다. 더 넓은 라이브러리나 보간한 새 램프를 지정했다고 `allowed_palette`나 `max_colors`가 완화되지는 않습니다. `palette_report.json`, 원본·최종 QA, `comparison.png`, 논리 변경 마스크 `changed_cells.png`, 입력·출력 해시로 변환을 추적합니다. 최종 PASS일 때만 출력 루트에 승인된 `native.png`와 `rendered.png`를 내보내며, 실패 후보는 진단용으로 남깁니다. 색상 병합이 눈·문구·윤곽·재질 구분을 지우지 않았는지는 별도로 검토합니다.

생성기는 기존 인라인 `palette`를 유지하면서 `palette_file` 참조를 대안으로 받습니다. 경로는 작화 JSON 폴더 안으로 제한한 상대 POSIX 경로이고, 행렬은 라이브러리의 색상 토큰을 사용합니다. `build.json`에 팔레트 원본 해시를 추가해 여러 작화가 같은 라이브러리 버전을 사용했는지 확인할 수 있습니다. 동봉 `palette-demo`는 같은 16×16·8배 규격에서 라이브러리 참조와 랜턴 색상 변환 경로를 설명합니다. 애니메이션·아틀라스·외부 엔진 연동은 이 변경에 포함하지 않습니다.

## v0.6.0: 스프라이트 시트·애니메이션과 선언형 부위 리그

프레임이 여러 개인 에셋은 한 장의 정적 PNG 시트에 같은 크기의 프레임 슬롯을 행 우선으로 배치합니다. 명세에는 프레임 크기, 열·행, 바깥 여백(margin), 프레임 사이 간격(spacing), 사용하는 프레임 수를 선언하고, 시트의 논리 크기는 이 값에서 계산합니다. 검사기는 기존 엄격 프로필로 시트 전체를 먼저 검사하고, 프로필의 `logical_size`가 계산한 시트 크기와 다르면 실행을 거부합니다. 여백·간격·빈 슬롯은 알파 0이어야 하며, 선택적 `edge_margin`은 프레임 가장자리에 붙어 잘리거나 옆 프레임으로 번지는 그림을 잡습니다. 시트의 셀 하나라도 단색이 아니면 프레임과 리그 검사를 진행하지 않습니다. 프레임 단위 판정이 대표색 추정에 기대지 않게 하려는 것입니다.

사용자가 요청한 핵심은 "인간형이면 골격을 가상으로 그려 부위의 도트가 일관되게 움직이고 유지되는지, 사물이면 움직이는 부분이 그렇게 움직이는지"입니다. 도트 그림에서 골격을 자동 추정하면 결과가 그림체와 해상도에 따라 달라지고, 검사기를 통과시키기 위해 해석을 바꾸는 여지가 생깁니다. 그래서 골격은 선언하고 검사기는 그 골격을 그려 비교하는 방식을 택했습니다. 이는 격자를 추정하지 않는다는 기존 원칙과 같습니다. 리그는 관절 이름과 프레임별 관절 좌표, 그리고 보이는 모든 도트를 부위에 배정하는 부위 맵으로 구성합니다. AI가 프레임의 색상 행렬을 작성할 때 같은 격자의 부위 맵과 관절을 함께 쓰는 것이 가장 정확합니다.

부위의 움직임은 네 종류로 나눴습니다. `fixed`는 모든 프레임에서 같은 도트, `rigid`는 회전축 관절이 옮긴 정수 칸만큼 이동한 정확한 복사본, `bone`은 두 관절 사이 뼈를 따라 옮긴 기준 도트, `free`는 존재·크기·색상만 확인합니다. 도트 그림의 팔다리는 회전하면 화가가 계단 모양을 새로 그리기 때문에 정확한 일치를 요구할 수 없습니다. `bone` 부위는 기준 프레임의 도트를 뼈 좌표(뼈 방향 비율, 뼈와의 수직 거리)로 옮겨 예측 위치를 만들고, 한 칸 이내에서 맞는 비율(`min_shape_match`), 뼈 기준 중심 이탈(`max_drift`), 뼈 길이 변화(`length_tolerance`), 도트 수 변화(`area_tolerance`)를 따로 판정합니다. 레버의 손잡이공처럼 회전하지 않는 부품은 `rigid`로 정확히 검사하고, 서랍처럼 한 방향으로만 움직이는 부품은 `axis`로 이동 방향을 제한합니다.

겹침은 도트 애니메이션의 기본이어서, 처음에 시도한 "가려진 부위 표시" 방식으로는 앞팔에 항상 일부 가려지는 몸통의 기준 프레임을 정할 수 없었습니다. 최종 설계에서는 부위를 뒤에서 앞 순서로 나열하고 그 순서를 깊이(z)로 씁니다. 부위의 도트는 더 앞에 그려지는 부위가 덮은 칸에서만 사라질 수 있고, 기준 프레임에서 가려졌던 영역에 새로 보이는 도트는 오류가 아닌 추가 정보로 다룹니다. 따라서 뒤에 그려진 몸통 속으로 앞팔이 사라지는 오류는 그대로 실패합니다. 프레임마다 그리는 순서가 바뀌는 동작은 프레임별 `z`로 덮어쓰며, 완전히 가려진 부위만 `hidden`에 적습니다. `hidden`으로 적어도 예상 위치가 빈 공간이면 실패합니다. 부모 연결과 관절 위치도 같은 깊이 규칙을 따릅니다.

기본 허용치는 실제 측정으로 정했습니다. 골격에서 래스터화한 걷기 예제의 정상 프레임은 형태 일치 97% 이상, 면적 0.85~1.12배, 이탈 0.67칸 이하였습니다. 반면 흔한 실수를 주입한 프레임에서 형태 기준으로 실패한 부위는 61~79%, 이탈로 실패한 부위는 1.70~2.90칸이었습니다. 이에 따라 형태 80%, 이탈 1칸, 길이 1칸, 면적 25%를 기본값으로 두었습니다. 얇은 대각선 부위는 1.4칸 정도 밀려도 한 칸 매칭을 통과하므로 이탈 지표를 별도로 두었고, 비교 가능한 도트가 6개 미만이면 중심 계산이 불안정해 이탈을 판정하지 않습니다. 한 칸 두께 변화와, 기준 프레임에서 대부분 가려진 얇은 부위의 두 칸 이동은 기본값으로 검출하지 못했습니다. 이 한계는 숨기지 않고 문서와 검증 기록에 남겼으며, 필요한 부위는 허용치를 낮추도록 안내합니다. 허용치 완화·`hidden` 추가·깊이 변경·부분 배정은 계약을 바꾸는 일이므로 사용자 동의 없이 통과 목적으로 쓰지 않도록 Skill에 명시했습니다.

빌드 명령은 프레임별 색상 행렬을 기존 생성기의 검증 규칙으로 해석해 투명한 여백을 둔 시트를 만들지만, 승인은 하지 않습니다. 검사 명령은 시트 검사 결과, 슬롯 배치 미리보기, 위 줄에 도트와 골격·아래 줄에 부위 맵과 골격을 보여 주는 리그 미리보기, 애니메이션별 GIF를 남깁니다. GIF는 재생 확인용 진단 자료이며 검사 대상 작품은 시트 PNG입니다. 입력 PNG 형식은 여전히 정적 PNG로 한정해, APNG의 첫 프레임만 검사하고 전체를 승인하는 일을 막습니다.

## 검증 전략

기존 19개 회귀 테스트를 먼저 통과시킨 뒤, 새 동작을 별도 검증합니다. 한 물리 샘플의 색상·알파 차이, 오프셋 격자, 직사각형 셀, 비정수 확대, 보이지 않는 RGB, 팔레트 밖 샘플, 애니메이션·포맷 거부, 원본 보호가 핵심 사례입니다.

생성기 테스트는 내보낸 PNG를 다시 열어 각 블록이 원래 논리 셀과 정확히 같은지 확인합니다. 배치 테스트는 손상된 파일이 있어도 나머지 항목을 검사하고, 중복 파일명으로 산출물이 충돌하지 않는지 확인합니다. 독립 에이전트는 Skill만 읽고 실제 요청을 실행해 안내와 산출물의 연결을 점검합니다. 플랫폼 호환성은 공식 문서에 근거한 패키지 설계이며, Claude 계정에서 실제 설치·실행한 결과와는 구분합니다.

레이어 테스트는 실제 픽셀의 앞뒤 순서와 투명 셀 보존, 정수 위치, 숨긴 불량 레이어의 거부, 레이어별 PASS 후 최종 팔레트·불투명 규칙 실패, 실패 시 승인 PNG 미출력, 원본·목록 보호를 확인합니다. 경로 이탈·잘못된 필드·해시 불일치·입력 크기 제한도 검증 대상입니다. 최종 저장 PNG가 논리 합성 결과의 정확한 정수 확대인지 기존 검사기와 픽셀 비교로 확인하며, 패키지에서 동봉 레이어 예제를 실행하는 경로도 검사합니다.

팔레트 기능의 검증 대상은 추출 순서와 잘림 기록, 숨은 RGB 정책, 같은 알파의 정확한 매핑, 램프 끝점·반올림·중복 거부, 지정 램프 제한, 기하·알파 보존, 원래 프로필 유지와 최종 목표 색상 검사입니다. 생성기의 인라인 방식과 라이브러리 참조 결과를 비교하고, 경로 이탈·원본 변경·출력 충돌도 확인합니다. 실제 실행 결과와 테스트 수는 버전별 검증 기록으로 관리하며 이 설계 설명 자체를 실행 증거로 삼지 않습니다.
